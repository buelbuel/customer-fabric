# Working on Customer Fabric

- Preserve the Go modular monolith and single backend module. Keep domain rules independent of HTTP and database drivers. Read relevant ADRs before architectural changes; read README and ADR 0001 before changing mutation semantics. Record major decisions in ADRs. Avoid speculative domains, infrastructure, SDKs and visual builders.
- Customer Fabric is unreleased: it has no production users, deployments or legacy integrations. Build the target design directly. Add no backward compatibility for unreleased APIs, schemas or storage formats, no expand–migrate–contract or rolling-upgrade and mixed-version support, and no shims or migration paths for hypothetical deployments. Still never silently destroy local development data: when a change cannot keep existing local rows, the migration refuses with a clear message, and resetting stays the developer's decision.
- Use parameterized SQL, pgx/v5, pgxpool, sqlc and goose. Keep profile, provenance and outbox writes atomic in a native pgx transaction. Never hand-edit generated queries.
- Kafka transports asynchronous tenant-scoped events from the PostgreSQL outbox and Temporal orchestrates durable workflows ([ADR 0013](docs/adr/0013-event-transport.md), [ADR 0014](docs/adr/0014-temporal-workflows.md)). Both stay opt-in for local development and CI, and never replace the PostgreSQL transaction/outbox. Do not dual-write a DB transaction and Kafka publish.
- Cloud target: shared SaaS staff/organization control plane but isolated tenant data planes (per-tenant business DB/credentials, customer issuer, Kafka ACL and Temporal isolation). Self-hosted OSS must not depend on Cloud. Read [Cloud target](docs/architecture/cloud-control-plane.md) and [event/workflow target](docs/architecture/eventing-workflows.md) before adding Cloud, Kafka or Temporal code or changing tenant, issuer or data-plane boundaries.
- Treat authentication, authorization and data provenance separately. Development auth must fail closed in other modes. Use synthetic data only; never log tokens, payloads or customer values.
- Never overwrite local environment files, copy real secrets to worktrees, or silently delete databases or volumes.
- Update OpenAPI and tests with endpoint changes. Verify changes before committing and disclose skipped checks. GitHub Actions is the verification gate.
- Preserve existing work and keep commits small and focused. Follow CONTRIBUTING.md: agents commit without `-s`, attribute with `Co-Authored-By`, never add any `Signed-off-by` (their own or a person's) and never call their work DCO-certified.
- Integration: open a PR and have a reviewer separate from the authoring agent review its final diff; fix actionable findings and re-review after substantive fixes. Unresolved findings block merging. Then arm auto-merge for routine synthetic-development changes; protection merges only when `backend`, `admin`, `customer-identity`, `contracts-and-images` and `operator-identity` pass on an up-to-date branch. Never weaken protection, bypass failed checks, suppress security tests or rewrite history. Leave merging to the maintainer for changes to AGENTS.md, CONTRIBUTING.md, skills, workflows or branch protection, and stop for the maintainer on real customer data, production credentials, deployments, billing, irreversible erasure/recovery, security-policy exceptions, unresolved critical vulnerabilities, legal certification or material scope changes.

Use the applicable procedures in [.agents/skills](.agents/skills) and the [local development guide](docs/development/local.md).
